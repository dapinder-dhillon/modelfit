**Small fixes I would make before tagging v1**

1. Update the README example from `CONFIDENCE` to the current `SIGNAL`. The README also says “Optimise this SQL query” will be called NEITHER; I ran that exact phrase and it now starts at `START       sonnet-5 / high effort`. The no-key quick start says it produces `reports/pareto.png`, while this installed base run said `Wrote reports/report.md, results.csv (install matplotlib for the chart)`. Make the chart conditional in that promise.
2. Update `lessons` copy. This run said `Most of your asks look routine — your default config should be the cheap one.` alongside `NEITHER 36, MODEL 21, BOTH 19, EFFORT 10.`. NEITHER is the largest group at 36/86, not a majority, and the default-config advice goes beyond those counts. Its standing warning still says crypto, SQL, timezone/DST, and concurrency all look boring; the current advisor catches explicit SQL, AES/nonce, and “at once” examples. Clearer wording would preserve the feature's honesty.
3. Make `--short`'s MODEL fallback specific, or tell users to use the default view for next steps. The compact blind-spot check now prints `haiku-4-5/off  [low — blind spot]`, which is a useful improvement. Yet the payment and SQL cases still say “escalate if needed” instead of “switch to opus at the same effort.” The README's promise that full warnings are never hidden behind a flag is too broad for a one-line view.

The sandbox history failure remains an edge case: advice printed, then the command exited with a traceback because the sandbox blocked `~/.modelfit/history.json`. It succeeded when the path was writable. I would keep a concise history-write error on the backlog; I would not hold this release for a failure seen only under that restriction.

The `lessons` calibration line in this workspace remains `Calibration: 0/1 recorded outcomes passed at the advised start config`. That one failure was the **synthetic outcome I recorded for the first review**, not a measured model result. I did not record another outcome in this rerun. The history also includes repeated QA prompts and other pre-existing asks, so its shape distribution should not be used as evidence for a production default.

**Release positioning I would use:** a local, deterministic starting suggestion for developers, with an offline mock and an optional benchmark on their own verifiable tasks. The current state is credible enough to invite early users and learn from them. Do not claim that the fixed regex rules have been shown to reduce cost or improve success until real tasks are measured.
